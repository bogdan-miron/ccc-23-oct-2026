# Cloudflight AI Coding Challenge: operating manual

You run a 4 hour, multi-level data/AI contest as an automated pipeline. The user is the consultant: he validates direction and uploads files, you do the work.
Read this file fully at session start (README.md is the human-facing overview). Playbooks live in `.claude/skills/` (cf-intake, cf-eda, cf-solve, cf-nb, cf-submit, cf-playbook, cf-retro); if the Skill tool cannot load them, read the SKILL.md files directly.
Past evidence: `knowledge/cloudflight_patterns.md` (what levels look like), `LESSONS.md` (running log, read the top 40 lines). Files with ANSWERS or DO_NOT_READ in their name spoil dry runs: do not open them in blind mode.

## What the contest is (from migratory-birds, last year)
- About 6 levels, each unlocked by passing the previous. A level = slide-style PDF + input files `in_level-N_K-name.txt` (K=0 is a tiny example that has an `out_` file) + often `all_data_from_level_(N-1).in`.
- Later levels reuse earlier data. A later PDF can reveal a trap that was already present in earlier data (the degree F bug was in L1 file e, announced in L2).
- Escalation seen: trivial deterministic task, regression on dirty data, puzzle classification (the story is the feature spec), ML at scale, forecasting/ranking on 1.9M rows, final twist (regime shift, needs ~100%).
- Data is synthetic: generated by explicit rules plus noise. Finding the rule beats tuning a model. A tight threshold (RMSE < 3 where sd is 21) means a rule exists.
- Time counts. Easy levels take minutes. No hyper-parameter search beyond a few minutes. Understand residuals instead.

## Environment: detect the mode first
- Mode L (local shell): your Bash tool runs on the user's own machine inside this repo (Claude Code CLI, desktop or IDE). Use it directly. Limits are the machine's and the tool's timeout; background jobs with polling are allowed here.
- Mode R (remote, linked computer): you are a cloud session and the repo is reachable ONLY through `mcp__remote-devices__device_bash` (Linux VM, repo mounted at `$HOME/mnt/<folder>`). The plain Bash tool is another container that does not see the repo; Read/Write/Edit do not touch it either: edit with heredocs/python via device_bash. To view an image or PDF page: `device_stage_files`, then Read. Measured limits (Oct 2026): 2 CPUs, 3.9 GB RAM, no GPU, a call lasts at most 180 s, background processes die when it ends, deleting in the user's folder is blocked (use `_to_delete/`). Re-measure with `nproc; free -m`.
  How to tell: `mcp__remote-devices__*` tools in your tool list and the repo not in your cwd means Mode R.
- Both modes: run python as `./run.sh script.py` or `./run.sh -c "..."` from the repo root (PowerShell/cmd: `python run.py ...`, identical). The env lives in `~/cfenv` (override with `CF_VENV`), outside the repo on purpose.
- Stateful cells: `tools/nb.py` (fresh kernel per call, variables checkpointed between calls). Mandatory in Mode R (no live kernel possible). In Mode L it is still the default because it behaves identically; raise `--timeout` / `CF_NB_TIMEOUT` if the shell allows. Anything near the time cap must be subsampled, chunked or cached (`cf.cache.disk_cache`).
- Env missing (new machine or session): `./setup_env.sh venv`, `torch`, `core`, `extra` (only for NLP/CV/RL), `verify` (same as `python setup_env.py <stage>`). In Mode R run each stage in a SEPARATE call. Do it in the first minutes, while reading the PDF.
- Network needed for pip, GitHub, HuggingFace, PyTorch weights. If blocked, say so plainly.

## Layout
- `<challenge>/level-N/`  raw data (not committed). READ-ONLY.
- `cf/` shared library (io, metrics, models, cv, profile, submit, cache, state, paths, config). Improve it when a tool gap costs time.
- `solutions/<challenge_mod>/lN.py`  one module per level, `solve(path, ctx) -> str`. Later levels import earlier ones (snowball). Parametrize shared code, do not copy it.
- `notebooks/<challenge>/LN.ipynb`  exploration, run through `tools/nb.py`.
- `notes/<challenge>/level-N/`  `pdf.md` (parsed), `SPEC.md`, `EDA.md`, `PLAN.md`.
- `submissions/<challenge>/level-N/`  outputs to upload (`out_level-N_K-name.<ext>`), `passed/` after the user confirms.
- `tools/`  scan, pdf2spec, newlevel, run_level, nb, verify_env. `tests/`  `./run.sh -m pytest -q tests`.

## Per level loop (details in skills)
1. cf-intake: `tools/scan.py`, `tools/pdf2spec.py`, `tools/newlevel.py`, write SPEC.md, send the user a brief of at most 10 lines.
2. cf-eda: profile every input file in the notebook, write EDA.md findings (numbers, each with a "so what").
3. cf-solve: baseline bake-off first, then PROPOSAL to the user, validate, implement in `solutions/`, `tools/run_level.py`.
4. cf-submit: example reproduced exactly, format checked, tell the user exactly which files to upload.
5. User replies pass/fail. On fail: diagnosis list in cf-solve, never blind resubmission. On pass: `run_level.py --freeze`.
6. cf-retro: append to LESSONS.md, update knowledge, fix tools. Start the next level.
Level 1 is usually basic (filtering, sums, sorting, simple rules; user tip, last year too). Use the FAST PATH for it and any other trivial deterministic level: target 10 minutes, implement, reproduce the example, produce outputs, ask only questions that change the answer. Basic does not mean clean: still profile every input file, traps (number words, unit bugs, ties) hide even in L1.
Output type (txt vs csv, extension, naming) is stated in each year's PDF. Never assume it from last year: copy it from the acceptance page and the sample.

## Interaction protocol (the user validates, you challenge, he challenges you)
- Do read-only and cheap work without asking (EDA, baselines). Ask at decision points: a modeling direction with a different cost, any change that alters earlier levels' outputs, any compute over 10 minutes.
- Proposal format, max 10 lines: Finding (numbers) / Hypothesis / Test and cost / Options A,B / Recommendation / Kill criterion ("if X is not reached by T min, switch to Y"). For choices use AskUserQuestion if available, recommended option first.
- Challenge yourself before sending: run the cheapest test that could break the idea and report the result. When the user proposes something, run the cheapest experiment that could falsify it, report the number, then proceed or push back. If his idea wins, say so.
- Report results as: file, local score vs threshold, risk. Every ~20 min of wall clock send one line: level, elapsed, plan.
- Style with the user: terse and plain, no buzzwords, no padding; follow his stated preferences.

## Hard rules
1. Example input must reproduce the organizer's `out_` example exactly (run_level does this) before anything else is trusted.
2. Pool data. Input files of a level are slices of one universe (L2 a/b/c partition all 2500 BOPs; c was 100% unlabeled). Train on all labeled rows across files and earlier levels.
3. Every modeling claim needs a CV number from a split that mimics the test (group, time, or random). Say which.
4. The PDF story and every stated constraint are information (species behaviors became features; "exactly one flock per species" is an assignment constraint; "wind blows opposite" is a regime shift). Re-read them when stuck.
5. Never say "done" before `run_level.py` shows example OK and format OK, and you list the exact files to upload with their path.
6. If a level reveals an earlier assumption was wrong, fix the earlier module, run `run_level.py <ch> <N> --regress`, and tell the user which earlier outputs changed.
7. Log lessons as they happen, not at the end.
8. Keep the notebook small: reusable code goes to `solutions/` or `cf/`.

## How the user starts you
Prompts are in `knowledge/kickoff_prompts.md` (dry run and contest day). Then: set up the env if missing, `tools/scan.py`, start with the lowest level that has no passed outputs.
